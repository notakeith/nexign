## Задача A. Теория Большого взрыва

Тестовый стенд: Apple M1 Pro, macOS 26.5.1, Apple clang 21.0.0.

```bash
$ sysctl -n hw.cachelinesize
128
```

#### Этап 1. Упаковка структур и выравнивание полей

Думаю, после упаковки структура будет меньше. Между полями в обычной структуре может оставаться свободное место.

1. Каковы размеры обычной и упакованной структур? Совпадает ли размер упакованной структуры с суммой размеров её полей?

```text
$ clang++ -std=c++17 -O2 -Wall -Wextra packing.cpp -o packing
packing.cpp:22:22: warning: taking address of packed member 'd' of class or structure 'PackedMixed' may result in an unaligned pointer value [-Waddress-of-packed-member]
   22 |     double* field = &p.d;
      |                      ^~~
1 warning generated.
$ ./packing
Mixed: 32 bytes
PackedMixed: 16 bytes
d offset: 16 / 6
Address of packed d: 0x16ddd60ce
```

В `Mixed` поля начинаются со смещений 0, 4, 8, 16 и 24. После последнего `short` ещё 6 байт, чтобы следующий элемент массива тоже начинался на границе 8 байт. В `PackedMixed` размер совпал с суммой размеров полей, `1 + 4 + 1 + 8 + 2 = 16`.

2. Если вы получили предупреждение или сообщение об ошибке при попытке взять адрес, приведите его дословно. Почему чтение невыровненного поля через указатель может быть проблемой?

В упакованной структуре `d` начинается со смещения 6. В этом запуске его адрес заканчивается на `0xce` и не делится на 8. Через обычный `double*` компилятор вправе ожидать выравнивание для `double`. Разыменование такого указателя в C++ даёт неопределённое поведение. В программе я только вывожу адрес. Если нужно прочитать значение, можно обратиться к `p.d` напрямую, тогда компилятор видит атрибут упаковки.

#### Этап 2. AoS и SoA

Я бы поставил на SoA. Цвет в этом расчёте вообще не нужен, а в SoA он лежит отдельно.

1. Какое время выполнения показал каждый вариант? Какое получилось ускорение SoA относительно AoS?

```text
$ clang++ -std=c++17 -O2 -Wall -Wextra particles.cpp -o particles
$ ./particles
run  AoS(ms)  SoA(ms)
1  9.642  5.414
2  9.544  5.395
3  9.579  5.442
4  9.541  5.523
5  9.604  5.366
10000000 particles OK
```

В обоих вариантах 10 млн одинаковых частиц. Перед замером сделал по одному шагу для прогрева, дальше чередовал порядок запуска. Таймер охватывает только один шаг. После пяти прогонов программа сверяет все три координаты каждой частицы с ожидаемыми.

Медиана AoS — 9,579 мс, SoA — 5,414 мс. Ускорение по медианам получилось `9,579 / 5,414 ≈ 1,77` раза.

2. Сколько полезных байтов приходится на одну кэш-линию при обработке данных в каждом варианте? 

В AoS полезны 24 из 28 байт частицы. На моём Mac линия 128 байт, значит, при длинном последовательном проходе в среднем используются `128 × 24 / 28 ≈ 109,7` байта на линию. Это среднее, потому что границы частиц и линий не всегда совпадают. В SoA все 128 байт полной линии используются, это 32 значения одного поля. Для линии 64 байта из примера получилось бы примерно 54,9 и 64 полезных байта соответственно.

3. Почему при обработке массива SoA компилятору проще использовать SIMD-инструкции, чем при обработке AoS?

Четыре соседних `x` и четыре соседних `vx` можно загрузить из двух массивов и сложить одной SIMD-инструкцией. В AoS между соседними `x` шаг 28 байт, поэтому собрать их в один вектор дороже. Это видно и по сообщениям Clang для двух циклов:

```text
$ clang++ -std=c++17 -O2 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize -S particles.cpp -o particles.s
particles.cpp:24:5: remark: the cost-model indicates that vectorization is not beneficial [-Rpass-missed=loop-vectorize]
particles.cpp:32:5: remark: vectorized loop (vectorization width: 4, interleaved count: 1) [-Rpass=loop-vectorize]
```

4. Для какого типа нагрузки вариант AoS может оказаться предпочтительнее SoA? Приведите пример доступа к данным, при котором это возможно.

Например, при обработке столкновения по индексу частицы нужны сразу её координаты, скорость и цвет. В AoS они лежат в пределах 28 соседних байт. В SoA пришлось бы обратиться к семи массивам, а при случайных индексах соседние элементы этих массивов могут больше не понадобиться. Для нашего последовательного шага я бы оставил SoA.

## Задача B. Вне конкуренции

#### Этап 1. Воспроизведение false sharing

Думаю, если разнести счётчики подальше друг от друга, получится быстрее. Если они лежат рядом, потоки могут мешать друг другу.

1. Какое время выполнения показал каждый вариант? Во сколько раз вариант B быстрее или медленнее варианта A?

```bash
clang++ -std=c++17 -O2 -Wall -Wextra -g -pthread -DCACHE_LINE_SIZE=$(sysctl -n hw.cachelinesize) counters.cpp -o bench
for run in 1 2 3 4 5; do
    if [ $((run % 2)) -eq 1 ]; then
        ./bench adjacent && ./bench padded
    else
        ./bench padded && ./bench adjacent
    fi
done
```

Каждый поток выполняет 100 млн `fetch_add(1, std::memory_order_relaxed)` над своим счётчиком. Таймер включает создание двух потоков и ожидание их завершения. В конце каждого запуска оба счётчика равнялись 100000000.

| Вариант, мс | 1 | 2 | 3 | 4 | 5 | Медиана |
|---|---:|---:|---:|---:|---:|---:|
| Рядом | 1662,20 | 1619,03 | 1628,96 | 1652,53 | 1318,17 | 1628,96 |
| Раздельно | 277,14 | 276,91 | 280,26 | 276,37 | 298,29 | 277,14 |

Ускорение по медианам `1628,96 / 277,14 ≈ 5,88` раза. В первом прогоне соседние счётчики имели адреса `0x16fb51f80` и `0x16fb51f88` (разница 8 байт). У разнесённых адреса `0x16d781f80` и `0x16d782000` (разница 128 байт).

2. Подтвердили ли вы, что потоки выполнялись на разных ядрах? Как именно?

На macOS потоки за ядрами не закреплял. В первом прогоне `adjacent` за 1662,20 мс реального времени процесс набрал 3310,41 мс процессорного времени, то есть в среднем занимал 1,99 ядра. Это подтверждает одновременное выполнение. Номера ядер и миграции потоков по этим данным определить нельзя.

3. Почему вариант A может работать медленно, если потоки изменяют разные счётчики и не обращаются к данным друг друга?

Когерентность кэшей работает на уровне целой линии. После записи первого ядра второму для записи своего счётчика приходится получить право менять ту же линию. При чередующихся записях она переходит от ядра к ядру. После выравнивания каждое ядро может многократно менять свою линию независимо.

4. Как, по вашему прогнозу, изменение числа потоков повлияет на проблему в варианте A? Почему?

Если каждому потоку дать свой 8-байтовый счётчик в том же массиве, в одной 128-байтовой линии поместятся 16 счётчиков. Чем больше ядер одновременно пишет в эту линию, тем больше конкуренция. Линейного замедления ожидать нельзя, оно зависит от числа работающих ядер и того, какие счётчики попали в одну линию.

#### Этап 2. Поиск false sharing с помощью perf c2c

Если дело в том, что счётчики лежат рядом, думаю, в отчёте будет видно, что оба потока пишут в одну кэш-линию.

1. В какой кэш-линии отчёт показывает наибольшую конкуренцию?

Профиль варианта `adjacent` снял на Ubuntu с Intel Core i5-3230M. По `lscpu` у CPU 0 и 1 разные номера ядер и один сокет. Команды для записи в файл и вывода отчёта:

```bash
sudo perf c2c record -o perf.data -- taskset -c 0,1 ./bench adjacent
sudo perf c2c report -i perf.data --stdio --no-source -d lcl -N -N -c tid,iaddr
```

По всему профилю `Rmt HITM = 0`. Оба ядра на одном сокете, и конкуренция видна в `Lcl HITM`. Больше всего таких попаданий у линии `0x7fffef0a3cc0` — 8670 из 8674 (99,95%). [Полный вывод perf c2c](artifacts/c2c.txt).

| Поле | Адрес | Смещение в линии | CPU | Записи, попавшие в профиль |
|---|---|---|---:|---:|
| `first` | `0x7fffef0a3cc0` | `0x00` | 1 | 14678 |
| `second` | `0x7fffef0a3cc8` | `0x08` | 0 | 12759 |

2. Как результаты `perf c2c` подтверждают или опровергают выводы, сделанные по времени выполнения на этапе 1?

На этапе 1 соседние счётчики работали медленнее. В профиле Ubuntu видно, что CPU 1 писал в первый счётчик, CPU 0 — во второй. Между адресами всего 8 байт, и почти все локальные HITM пришлись на их общую линию. Это подтверждает объяснение замедления через false sharing.
